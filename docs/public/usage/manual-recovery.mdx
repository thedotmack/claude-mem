# Manual Recovery Guide

## Overview

The observer keeps live work in an in-memory buffer and does **not** replay it automatically after a crash. That is deliberate: a buffered input is one tool-use fragment fed to a stateful, non-deterministic reducer, and replaying fragments without the reducer state used to produce duplicate observations and retry storms.

The Claude Code transcript JSONL is the durable source of truth. Recovery is an explicit action you take, not something the worker performs on startup, on a timer, or after a quota reset.

## When Do You Need Manual Recovery?

Trigger recovery when:

- **The worker crashed or restarted** and observations were queued but never processed.
- **Observations are being saved but no summaries appear.**
- **`/api/processing-status` shows work that is not moving.**
- **`lastSuccessfulStoreAt` is old** while the worker still reports healthy.

## Quick Start

### Using the CLI Tool (Recommended)

```bash
# Check status and prompt before recovering
bun scripts/check-pending-queue.ts
```

```bash
# Recover without prompting
bun scripts/check-pending-queue.ts --process
```

The CLI checks worker health, reads `/api/processing-status`, shows what is pending, and asks before it starts generators.

### Using the HTTP API

```bash
WORKER_PORT=$(jq -r .CLAUDE_MEM_WORKER_PORT ~/.claude-mem/settings.json)
```

**Check status:**

```bash
curl http://127.0.0.1:$WORKER_PORT/api/processing-status
```

**Trigger processing:**

```bash
curl -X POST http://127.0.0.1:$WORKER_PORT/api/processing \
  -H "Content-Type: application/json" \
  -d '{"isProcessing": false}'
```

`POST /api/processing` is localhost-only and rejects a foreign browser page on another local port. It starts pending generators and retries the auth/transport pauses that the automatic sweep leaves alone.

## What the Status Reports

`GET /api/processing-status` returns:

| Field | Meaning |
|---|---|
| `isProcessing` | Whether any session is currently generating |
| `queueDepth` | Total live work waiting or in flight |
| `parkedSessions` | Sessions waiting for a concurrency slot |
| `lastSuccessfulStoreAt` | Last time an observation was stored, or `null` |
| `abandonedStallSessions` | Sessions the response-stall pacer abandoned, with the messages they hold |
| `expiredObserverInputs` | Live inputs discarded by expiry over this worker's lifetime |

`expiredObserverInputs` and `abandonedStallSessions` are the honest signal that a burst outran the observer. Expired work is never replayed.

## What Recovery Can and Cannot Do

**Can:**
- Start generators for pending sessions.
- Retry pauses that the automatic sweep leaves alone.

**Cannot:**
- Replay inputs discarded by quota or authentication pauses.
- Replay inputs that expired out of the in-memory buffer.
- Reconstruct reducer state from a last observation ID, a delivery receipt, or a pending fragment.

If an input was discarded, the transcript remains on disk and can be reviewed manually, but claude-mem will not replay it on its own.

## Best Practices

### 1. Check Before Recovering

```bash
bun scripts/check-pending-queue.ts
```

### 2. Recover One Burst at a Time

Start a recovery, watch `queueDepth` fall, and only then trigger another. Repeated triggers do not make a stuck generator faster.

### 3. Watch the Logs

```bash
npm run worker:logs
```

Look for generator starts, processing completions, and errors.

### 4. Verify With `lastSuccessfulStoreAt`

```bash
curl -s http://127.0.0.1:$WORKER_PORT/api/processing-status | jq '.lastSuccessfulStoreAt'
```

A moving timestamp is the real proof that storage recovered.

## Troubleshooting

### Recovery Not Working

1. **Verify worker health:**
   ```bash
   curl http://127.0.0.1:$WORKER_PORT/api/health
   ```
2. **Check logs for errors:**
   ```bash
   npm run worker:logs | grep -i error
   ```
3. **Restart the worker:**
   ```bash
   npm run worker:restart
   ```

### Work Keeps Expiring

A rising `expiredObserverInputs` means more sessions are producing work than the observer can batch. Reduce the number of parallel sessions or raise the observer limits in settings, rather than triggering recovery repeatedly.
