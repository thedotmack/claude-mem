# Claude-Mem 16.0.0 release instructions

## Maintainer direction

The next planned public release is **Claude-Mem 16.0.0**. Direct import from
**Mem0 Platform and Supermemory** is an anchor feature, not a separate utility
to leave outside the shipped CLI. Put the implementation through community
and reviewer feedback before inclusion. Do not auto-merge this PR, publish a
tag, publish npm or deploy anything as part of opening it.

## User-facing result

With an existing worker running and a source key in their environment, users
can run one command to bring a selected source user or namespace into a
Claude-Mem project. They do not need to export or transform a file manually.

```bash
npx claude-mem import --from mem0 --source-account personal-mem0 --user USER_ID --project imported-memory
npx claude-mem import --from supermemory --source-account personal-supermemory --namespace NAMESPACE --project imported-memory
```

Use `MEM0_API_KEY` or `SUPERMEMORY_API_KEY` respectively. Support `--dry-run`
for preview and `--documents` for Supermemory source-document text. Preserve
the documented distinction between a one-time import and ongoing sync.

## Review and acceptance

- Review the collector against the current Mem0 v3 and Supermemory v5
  contracts, including authorization, selected scope, complete pagination,
  response limits, and current-versus-forgotten/superseded memory behavior.
- Review original IDs, timestamps and metadata preservation, source-account
  separation, exact project scope, and deterministic repeat-import handling.
  Exercise a lost save response and resume the same import without duplicates.
- Confirm source keys never reach the worker or logs. Verify worker
  authentication and excluded-project refusal. No production memories or
  customer credentials belong in fixtures, review comments or CI.
- Run `bun test tests/npx-cli/import-memory.test.ts`, `npm run typecheck`,
  `npm run build`, and `python3 tests/fixtures/import-provider-smoke.py`.
  Check the packed npm artifact, committed bundle/version tests, and normal
  CI, including the broader regression suites.
- Reviewers may test an owned synthetic Mem0 user or Supermemory namespace
  using their own authorized credentials. Record sanitized outcomes and exact
  versions. The submitted vendor side is simulated HTTP; it does not prove a
  live vendor account migration. Do not claim that verification prematurely.
- Resolve reviewer feedback and any CI failures before maintainer signoff.

The local broad fast-suite run did **not** complete: automatic review blocked

## Release procedure after approval

1. Merge only after community/reviewer feedback and maintainer approval.
2. Confirm the final release tree keeps package and shipped plugin versions
   synchronized at `16.0.0`. Regenerate bundles through the normal build.
3. Run release CI and clean-room verification on the final tree. Test the
   packed package's two import commands and help text.
4. Lead the release notes with **Bring your existing memory: import from
   Mem0 and Supermemory**. Include setup, `--dry-run`, replay behavior and the
   documented one-way import limits. Link `docs/public/usage/import-providers.mdx`.
5. A maintainer must explicitly authorize tagging/publication at that point.
   The `v*` tag workflow publishes to npm; do not push a tag merely to request
   review. Confirm the published package and release notes only after the
   publication workflow succeeds.

The current user request authorizes opening this review PR and recording the
release plan. It does not authorize releasing an unreviewed candidate.
