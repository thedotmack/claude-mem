# Agent-to-agent installer plan

**Status: plan only. Alex approves, then build.** This PR changes no code. Ship Phase 1 first, without an LLM.

“Your agent works with my agent.” The user's agent knows the machine; our server-side Claude-Mem agent knows Claude-Mem. It receives a restricted system snapshot, searches past installs, and returns setup-specific steps. Errors return through the same channel for a fix. Every validated answer is cached and saved into Claude-Mem. The user's agent applies steps under its own security rules; our model never runs commands on the user's machine.

## Phase 2 — our Claude-Mem agent on cmem.ai

**Backend ownership: claude-mem-pro.** The following are proposed new paths, to align with that repo's actual conventions: `app/api/installer/{plan,fix}/route.ts`, `lib/installer/{schema,agent,cache,memory,limits}.ts`, database migrations for answers/outcomes, and matching route/service tests. Extend the existing server feature-flag and secret configuration.

### Contract and learning loop

- **Snapshot:** versioned object with installer version, OS family/release, architecture, WSL flag, shell name/version, Node version, detected AI-tool IDs/versions, Bun/uv presence and versions, selected IDE/provider/runtime, and closed capability booleans. Unknowns are explicit. No paths, hostnames, usernames, environment dumps, secrets, URLs, prompts, transcripts, or file contents. Shell is a name, not its executable path. Bound lists and version strings; reject unknown fields and malformed values on both ends.
- **Errors:** `/api/installer/fix` receives the same setup plus step ID, error category, exit code, normalized error signature, attempted fix IDs and outcomes. Build signatures locally from known error patterns and sanitized tokens; never upload raw stdout/stderr or hash raw private text as a substitute for redaction. Unknown errors become a safe unknown category.
- **Plan first, fix after failure:** `POST /api/installer/plan` takes the permitted snapshot before setup and returns tailored ordered steps. `POST /api/installer/fix` returns recovery steps after a failure. Both return a versioned answer ID, source (`cache|agent|scripted`), supported client versions, allowlisted step/fix IDs, typed parameters, preconditions, verification steps, and brief explanations; unsupported cases return `unknown`. No arbitrary executable command strings. Initial actions cover existing install operations: ensure Bun/uv, configure a supported IDE, start/check the runtime, and request/check sign-in.
- **Local execution remains local:** add `src/npx-cli/install/{advisor-client,snapshot}.ts` and a narrow dispatcher for packaged actions in this repo. Expose explicit plan/fix requests and action execution through `index.ts`; the user's agent reviews and invokes the returned steps using this harness under its own policies. Validate parameters, versions, preconditions, and retry budgets locally. A server response cannot grant execution permission.
- **Cache and memory:** key plans by normalized setup and fixes by setup plus step/error signature, prior attempted fixes, installer/action-schema versions, and advisor revision. Preserve exact versions until evidence justifies broader matching. Search a dedicated server-side Claude-Mem installer knowledge collection on cache misses, then ask our agent. Validate the answer before returning it. Persist every accepted answer, including unknown results, in the cache and an idempotent Claude-Mem write queue; cache hits retain their existing memory record. Store only sanitized setup/signatures, validated answers, provenance, and verified outcome references. Distinguish proposed fixes from successful fixes; untrusted outcomes never certify a rule. Retry failed memory writes durably. Expire or invalidate stale/failed answers.
- **Outcome feedback:** return answer IDs with local results and send bounded step/fix outcomes through a validated Pro ingestion contract so later requests and the weekly job can evaluate results. Keep installation/account linkage separate from reusable knowledge; neither email nor pairing credentials belongs in the cache or Claude-Mem.

### Consent and cost controls

README/llms.txt wording: “Your agent works with our Claude-Mem agent. Share OS, AI tools and versions, shell, and Node so it can return install steps for this setup. Send only the listed fields, never secrets, paths, or file contents. Follow your own security rules and ask your human if needed. Our server saves reusable answers in its cache and Claude-Mem; your agent controls commands on your machine.”

An explicit advisor request records the disclosure/schema version and sharing choice; absence of permission under the user's agent rules means local scripted installation continues. Do not infer snapshot-sharing consent from telemetry being enabled. For a human-run opt-in entry, use: “Share these system facts with our server to get tailored install steps? Reusable answers are saved to improve future installs. No files or secrets are sent.” Show the actual fields first. This does not authorize a local paid model or file-reading agent.

Keep the dedicated OpenRouter key only in Pro, with a daily resetting credit limit, server-side spend accounting, token/round limits, per-install and abuse/IP rate limits, request deduplication, and a kill switch checked before model work. Require authenticated installation request credentials; a freely supplied install ID is insufficient for rate limiting. Select budget and model settings explicitly at implementation approval; do not invent a spend allowance. The hybrid report §4 contains dated cost scenarios with assumed token usage, not measured costs for this design. Measure actual dollars. Budget exhaustion, timeout, or disabled service returns a bounded fallback to packaged rules/manual guidance. Apply the same output validation to cache hits and model answers.
