## What changed

| Area | Files | Summary |
| --- | --- | --- |
| 1. Canonical validators | `src/services/sync/CanonicalContent.ts`, `services/sync-api/src/canonical-content.ts` | `metadata.cmem_media_v1` is validated whenever the key is present. Local code uses the shared `validateMediaManifest`. The sync-api has a self-contained copy, because its Dockerfile ships only `src/`. An explicit `null` is **invalid**, matching Pro. Other metadata namespaces pass through unchanged. Unknown top-level payload fields stay rejected. Payload schema 2 and the 256,000-byte budget are unchanged, and there is no new ContentKind. The sync-api still forwards exact bodies and hashes. The legacy Workers hub is untouched. |
| Schema v63 | `src/services/sqlite/media.ts` | `media_attachments` gets new columns: `origin` (`native`/`replica`), `upload_attempts`, `upload_retry_at` and `upload_error`. They are added with `ADD COLUMN`, so the v61 CHECKs are kept. New `media_cloud_deletions` outbox. The delete triggers are now created after those columns, and each unreferenced-attachment cleanup queues a cloud deletion when the attachment was `uploaded`, or was `pending` with at least one attempt (a response may have been lost). |
| 2. Upload/retry worker | `src/services/media/cloud.ts` (`MediaCloudClient`, `MediaCloudSync`), `src/services/worker/DatabaseManager.ts` | A separate unref'd 30 s drain, independent of `CloudSync`. Deletions drain before uploads. Uploads go to native `ready`+`pending` rows only, gated on `CLAUDE_MEM_MEDIA_CAPTURE_ENABLED === 'true'` and cloud sync being configured. The predicate is the exported `isCloudSyncConfigured` from `CloudSync.ts`, which `DatabaseManager` now uses too. Deletions drain whenever credentials exist. Transport copies CloudSync: the bearer is `CLAUDE_MEM_CLOUD_SYNC_TOKEN` (a `cm_pro_` setup token, which Pro's `authenticateHookBearer` accepts), with injectable fetch and a per-request timeout. The base URL is the existing `cmemProOrigin()`. The route and multipart shape are copied from Pro's `cloud-routes.ts`/`cloud-contract.ts`: `POST /api/observation-media` with exactly `manifest` and `canonical` (`image/webp`), and the manifest is `{version,id,provenance,canonical,encoder}`. The owner-only `source_locator` is stripped. Retries use exponential backoff from 30 s, capped at 1 h. The attempt count is written before each request (lost-ack tracking), but **transient failures never consume a budget**: network errors, timeouts, 401/402/403, 429 and 5xx, plus `media_not_ready`, `quota_exceeded` and `conversion_busy`, back off indefinitely at a 1 h cap. Only deterministic failures are final: `checksum_mismatch`, other 4xx and a cloud tombstone (404). Completing an upload changes only `upload_state`: it never touches observation text, metadata, `sync_rev` or `synced_at`, and never re-observes. |
| 3. Second-device replica | `src/services/media/replica.ts`, `src/services/sync/SyncApply.ts`, `MediaStore.isUnresolvedReplica`/`publishReplica`, `MediaCloudReplicaResolver`, `MediaRoutes` | Every **accepted** replica observation insert or update mirrors its manifest. Each ID gets a placeholder row (`origin='replica'`, `upload_state='cancelled'`, so it is never uploaded; `failure_code` NULL) and a junction row. `MediaStore.getMetadata` reports an unfetched placeholder as the distinct state **`unresolved_replica`**, never `failed`. The DB row keeps `state='failed'` because the committed v61 `state` CHECK has no spare value, and a CHECK rebuild would mean an FK-off table rebuild; any count of failed media must filter `origin='native'`. Downloads are capped at 4 concurrent; extra reads fail fast as pending. Refs dropped by a newer revision are unlinked and tombstoned locally. Cloud-side removal of dropped refs is Pro's projection plus retention (commented in `replica.ts`). Stale ops never reach this code. On the first viewer read (`GET /api/media/:id[/variant]`), the resolver fetches the authorized descriptor and both variants from Pro, verifies length and SHA-256 against the descriptor, and publishes them with the same atomic staged rename. It is single-flight per ID. Cloud 404, offline and auth errors read as `media_not_ready` (409), because Pro has no existence oracle. Removal arrives as the text tombstone. A replica deleted mid-download is not resurrected. |
| 4. Deletion | triggers above, `MediaCloudSync.drainDeletions`, post-upload check | Local item and session deletion use the existing sync-safe routes and triggers. Project deletion has no local route; it removes sessions, which fire the same triggers. A never-attempted pending upload of a deleted source becomes `cancelled`, with no cloud call. A native image that was uploaded, or that had **any** upload attempt (including a `failed` one, whose ack may have been lost), gets a durable cloud `DELETE /api/observation-media/{id}`. 204 or 404 means done; every other result backs off at a 1 h cap and is never parked or dropped. A deletion that lands while an upload is in flight is caught twice: by the trigger (the attempt is counted before the request) and by the post-upload `UPDATE … WHERE upload_state='pending'` check. Replica deletions never queue cloud deletions. Account erasure is Pro's Phase 3 store; locally, removing credentials stops all media cloud traffic. |
| 5. Prompt/transcript media | `reports/image-aware/phase-5-capture-matrix.md` | No fixture-proven prompt or transcript-record image events exist, so these are documented as unsupported and no prompt capture was added. `submittedPrompt:null` semantics are unchanged (regression test run). Transcript tool results already reach the Phase 2 seam with `call_id` as identity; this is shape-supported but has no Codex image fixture. |
| Added scope: Cowork hook client | `cowork/scripts/cmem-hook.mjs`, `cowork/config.json` | Final Pro upload shape (see Unmet). Off by default. It is enabled **only** by its own switches, `capture.media: true` in `config.json` or `CMEM_MEDIA_CAPTURE_ENABLED=true`. A local claude-mem `CLAUDE_MEM_MEDIA_CAPTURE_ENABLED` does not enable it. It runs a bounded walk of a structured clone of the **raw** `tool_response`, before `clean()`. It recognizes four shapes (Anthropic, Read at `/tool_response`, MCP, OpenAI data URL) and sniffs PNG/JPEG/WebP magic bytes against the declared MIME, at most 3 MiB, keeping the first 4. Each block is replaced by `{type,cmem_media:'event1_imageN'|'unsupported'|'upload_failed'}`. Each image is uploaded before the first ingest, keyed by `platform:'cowork'` and `{kind:'platform_event',id:tool_use_id}` with a random UUIDv4, within a 15 s budget. On failure the envelope is staged once as text-only, and the spool never retries the upload. If the bounded walk hits its node or depth limit, an iterative linear pass strips every remaining recognized block (and data URLs in strings) before `clean()`. If cloning fails, a serialized scrub replaces data URLs and long base64 runs. An upload failure writes one bounded code to stderr, such as `media upload failed (storage_unavailable)`, never ids, labels or bytes. No bytes reach `truncate`, redaction, the envelope, the spool or logs. Without a valid `tool_use_id`, bytes are stripped and nothing is uploaded. |

Checklist evidence (`tests/media/media-sync.test.ts`):

- **L→hub→second-device round trip.** A real CloudSync push goes through a mocked hub log into a real SyncClient/SyncApply on device B. Metadata (manifest plus the other namespace) is equal on both devices. The pushed body contains no `data:image`, `base64`, path, `.webp`, provenance hash or event identity. The junction mirrors the manifest. The viewer route returns 409 pending before the owner upload, then 200 with bytes identical to the owner's after it. A foreign Origin gets 403 before any cloud call.
- **Text before media, then ready without duplication.** The upload drain leaves `sync_rev`, `synced_at` and metadata byte-identical. Observations stay at 1 and there are 0 unsynced rows. A second drain does not upload again. No observer or model is involved anywhere.
- **Offline spool, reconnect, lost ack, checksum mismatch and replay keep stable IDs.** Offline increments attempts and sets a backoff, and nothing runs inside the window. A lost acknowledgement followed by a retry gives one server object with the same ID. Re-capturing the same event reuses the ID. A 503 retries; 409 `checksum_mismatch` and a cloud tombstone are final. A corrupted replica download is rejected as `checksum_mismatch` and stays resolvable.
- **The replica is never re-uploaded or echoed.** B's media drain makes 0 uploads, and B's CloudSync flush pushes 0 ops.
- **Offline deletion then a delayed upload cannot recreate the image.** A cancelled never-attempted upload makes 0 cloud calls. Uploaded and lost-ack images are deleted through the durable outbox across an offline failure. An in-flight deletion leaves the cloud copy tombstoned. Observation deletion alone keeps event-retained media.
- **Stale refs cannot recreate or delete media.** A stale rev cannot add an image. A newer rev replaces the refs. A higher-revision tombstone removes links and queues no cloud deletion. A stale live op after the tombstone recreates nothing.
- **Mutation checks.**
  - Disabling the trigger's cloud-deletion queueing fails the deletion test.
  - Disabling replica linking on update fails the stale/replace test.
  - Removing only the post-upload deletion insert did **not** fail the in-flight test, because the trigger already covers that case. It stays as defence in depth.

## Unmet or open

- **Cowork upload shape is final, and it follows Pro's spec** (`claude-mem-pro` `reports/image-aware/phase-5-pro.md`, client spec step 4). The body has exactly two fields. `manifest` is `{version,id,provenance{…platform:'cowork',event_identity:{kind:'platform_event',id:tool_use_id},…,recipe:'screenshot-v1'},canonical{sha256,width,height,byteLength},encoder:'source'}`. `canonical` is the decoded source bytes, typed by their magic bytes (`image/png|jpeg|webp`). Dimensions come from the PNG IHDR, the JPEG SOF0/SOF2 frame, or the WebP VP8/VP8L/VP8X header, before EXIF orientation. An image over 8192 px or 24,000,000 pixels is never uploaded. The attachment ID is a random UUIDv4 created once per image per invocation. There is no in-invocation retry, and an upload is never retried from the spool. **Deviation to confirm:** `source_pointer` is rooted at `/tool_response`, as in the local worker scanner, so that the root-level Claude Read result (`/tool_response`) has a grammar-valid pointer. Pro's example is `/content/0`, relative to the response. Pro validates only the grammar and finds images by event key, so both forms are accepted. **The lane stays off** until a real Cowork PostToolUse image fixture exists; the tests use the local native shapes with generated pixels.
- **The local upload worker targets the current WebP-only Phase 3 contract.** If Pro changes the route, `MediaCloudClient.upload` (canonical WebP plus `encoder`) must stay accepted or be updated.
- **Pro status route not used.** Local replica resolution uses descriptor and variant reads, not Pro's new `GET /api/observation-media/status`. A cloud 404 therefore always reads as pending locally.
- **L→hub→P→viewer/MCP was not run end to end.** P's projector and leakage tests are on the P side. L proves only the L half, with mocked hub and Pro.
- **Event-level-only media never produced an observation.** Locally it follows Phase 2 event retention; cloud-side it follows the Pro 30-day orphan grace. No local cloud event-delete call was added: attachment-level deletes plus text tombstones cover every local deletion path.
- **Replica DB state.** An unresolved replica is still `state='failed'` in SQLite. The API state is distinct, but direct SQL consumers must filter `origin`.
- **Replica edge case.** If a replica ID is re-referenced while its cleanup job is still pending, it stays deleted, so the read returns 404 until a later revision touches it.
- **Pre-existing test harness.** `cowork/test/run-tests.mjs` uses `/tmp/cmem-testhome`. That is pre-existing and was not changed; the new Cowork test uses `.scratch`.
- **Scratch PostgreSQL.** The cluster is stopped. Restart with `pg_ctl -D .scratch/pg-sync-api/data -l .scratch/pg-sync-api/server.log -o "-h 127.0.0.1 -p 60665 -c unix_socket_directories=''" start`, then `DATABASE_URL=postgres://postgres@127.0.0.1:60665/sync_api_test bun run test` in `services/sync-api`.

## Contract defects / coordination (contract not edited)

1. **Null namespace.** The doc does not say whether `cmem_media_v1: null` is absent or invalid. L, the sync-api and P now all reject it. This needs a one-line clarification in both repos.
2. **Capture matrix is frozen.** The rows still say "capture implementation still disabled". The L matrix lives in `phase-5-capture-matrix.md` until a coordinated doc update.
3. **Pro upload contract now has a second canonical form.** It accepts unconverted `encoder:'source'` PNG, JPEG or WebP parts (Pro decision). The frozen doc still describes only WebP plus a `sharp-…/vips-…` encoder, and it needs the coordinated update. The local worker keeps the WebP/Sharp form.
4. **Event identity differs between the two lanes.** The local worker namespaces the tool-use ID by `(platform, contentSessionId, toolUseId)`. The Cowork client uses the raw `tool_use_id`, because Pro's observer looks images up by `eventKeyFor('cowork', {platform_event, tool_use_id})`. Both lanes are internally consistent, but the same tool use reaching both lanes would get different event keys.
